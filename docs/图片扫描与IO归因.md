# 图片扫描：分批执行、结果缓存与 IO 归因

## 解决什么问题

数万到数十万文件的目录树，一次完整扫描会连续占用事件循环：扫描期间页面点击、缩略图请求和其它接口都要排队，表现为「点了没反应」。
本机制把扫描拆成小段执行、把结果缓存在进程内，并提供 IO 归因接口，用来回答「谁在占 IO、卡在哪个环节」。

## 哪些请求会读盘

| 请求 | 读盘方式 |
| --- | --- |
| `GET /api/images?recursive=true` | 按目录索引：每层读索引，只有修改时间变过的目录才重读（见 [目录与索引机制](目录与索引机制.md)） |
| `GET /api/images`（不递归） | 只读该层一个目录 |
| `GET /api/dir` | 优先复用最近一次递归结果的内存快照；没有快照时只读该层一个目录 |
| `GET /api/zip/scan`、`/api/zip/img`、`/api/zip/gif` | 读压缩包，不走图片扫描 |

## 分批执行

- 逐层读取目录，按「目录 → 子目录 → 文件」的顺序收集图片；每处理一批目录主动让出一次事件循环，其它请求可以插进来执行。
- 单张图片读失败（无权限、扫描中被删除）只跳过该文件，不中断整轮。
- 目录不存在或为空时返回空列表，不报错。
- 排除目录不进入；命中所配置浏览黑名单的路径直接拒绝（403），不读盘。

规模参考：约 7 万张图的目录树，一次完整扫描约 2.1 万次目录读取与 7.2 万次文件属性读取，合计约 1.8 秒；分批执行后，同一轮扫描期间的接口延迟在几十毫秒级，不再出现近 2 秒的整段阻塞。

## 结果缓存与刷新

- 递归列出的图片会按请求目录在进程内存里留一份快照，`/api/dir` 直接从中切片，不必重扫。
- 快照没有固定过期时间：下一次递归请求按目录修改时间重建它；进程重启后清空。
- 强制刷新：给 `/api/images` 加 `noCache=true`，跳过缓存重新收集。页面上传完成后会自动这样请求一次。
- 目录内容变化（新建、删除、改名、替换文件）会在下一次递归请求时反映出来，依据是目录修改时间。

## 可配置项

| 配置 | 位置 | 默认 | 作用 |
| --- | --- | --- | --- |
| `excludeDirs` | `server/config.json` | `["@eaDir"]` | 扫描时跳过的目录名（群晖缩略图目录等） |
| `GALLERY_BLACKLIST_DIRS` | `.env` 或启动环境 | 内置系统目录集 | 命中黑名单的路径直接拒绝（403），不进入扫描 |
| `noCache` | `/api/images` 请求参数 | 空 | `true` 时跳过结果缓存 |

扫描没有单独的总开关：始终按需执行，缓存随进程存在。

## 可查接口

### `GET /api/io`（需登录）

返回进程的真实读写速率与按来源的累计量：

| 字段 | 含义 |
| --- | --- |
| `rate.readMBps` / `rate.writeMBps` | 最近一个采样窗口内的平均读写速率（MB/s） |
| `self.readBytes` / `self.writeBytes` | 进程启动以来的累计读写字节 |
| `byLabel` | 按来源汇总的累计量：`scan:readdir`（目录读取）、`scan:stat`（图片属性读取）、`probe:stat`（缓存探针） |
| `bySite` | 按调用点汇总的累计量与调用次数，用于定位具体环节 |
| `intervalMs` | 采样间隔，默认 10000 毫秒 |
| `enabled` | 读不到 `/proc/self/io`（非 Linux）时为 `false`，此时只有自报计数 |

```bash
# 未登录会被拒：先在设置页登录，再带上会话 Cookie 请求
curl -s 'http://<NAS-IP>:<端口>/api/io'
```

日志：每 10 秒采样一次，读或写速率超过 2 MB/s 时打一行 `[io]` 日志，带当前最热的调用点。

## 已知限制

- 扫描结果整份留在内存（每个请求目录一份），十万级目录树的内存占用随图片数量增长；响应不是边扫边返回，要等整轮结束。
- 不跟随符号链接目录：软链目录不进入，软链图片按普通文件处理。
- 扫描是同步文件读取，分批只降低「堵住服务」的时间，不提升总吞吐。
- `byLabel` / `bySite` 目前只登记扫描路径；按目录索引的读盘没有登记，两张表为空说明当前没有走扫描路径。

## 出问题时怎么判断

1. 页面卡、接口慢 → 查 `/api/io`：`rate.readMBps` 持续偏高时看 `bySite` 前三名，同时看启动日志里的 `[io]` 行。
2. 想立刻减负 → 把能排除的系统目录加进 `excludeDirs`，或收窄浏览范围。
3. 图不更新 → 带 `noCache=true` 重新请求；仍不更新时检查目录修改时间是否真的变了（SMB/挂载场景下修改时间更新有延迟），必要时删除 `cache-index/<分类>/index.jsonl` 后重试。
4. 请求 `/api/io` 返回 401 → 该接口需要登录。
5. 内存持续上涨 → 确认浏览目录数量与图片规模，可重启服务清空快照。

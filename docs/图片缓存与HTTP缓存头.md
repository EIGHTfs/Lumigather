# 图片缓存：HTTP 缓存头与条件请求

## 解决什么问题

浏览器每次刷新都重新下载图片：既费流量，也让首屏等待变长。
现在图片响应带上缓存指纹与有效期，未变更的图片在有效期内直接复用本地副本；过期后服务端只回一个空的 `304`，不重传字节。

## 怎么工作

- 每个图片响应带三个头：`ETag`（文件大小 + 修改时间）、`Last-Modified`、`Cache-Control: public, max-age=<秒>, must-revalidate`。
- 有效期内浏览器直接用本地副本，不发请求。
- 超过有效期后浏览器带上 `If-None-Match`（或 `If-Modified-Since`）再问一次：
  - 文件没变 → `304`，响应体 0 字节；
  - 文件变了（大小或修改时间变化）→ `200` 加新的完整内容。
- 判定顺序：`If-None-Match` 优先于 `If-Modified-Since`；`If-None-Match` 支持 `*`、逗号分隔的多个值与 `W/` 弱校验写法。
- 页面 HTML 与 JSON 接口仍是 `no-cache`：数据要即时，不参与这套缓存。

## 哪些接口带缓存

| 接口 | 内容 | 有效期 | 条件请求（304） |
| --- | --- | --- | --- |
| `/api/media` | 单张图片 | 读配置，默认 3600 秒 | 支持 |
| `/api/zip/img` | 压缩包内图片 | 内置 3600 秒 | 不支持，过期后整份重传 |
| `/api/gif`、`/api/zip/gif` | 合成 GIF | 内置 3600 秒 | 不支持，过期后整份重传 |

压缩包内图片的指纹取「压缩包大小 + 压缩包修改时间 + 条目长度」：换图或重新打包后指纹变化，不会继续显示旧图。

## 可配置项

| 配置 | 位置 | 默认 | 说明 |
| --- | --- | --- | --- |
| `mediaCacheMaxAge` | `server/config.json` | 3600 | 单张图片的缓存秒数；设 `0` 表示每次都要回源校验（内容未变时仍回 304） |

改完重启服务生效；其它三个接口固定使用内置的 3600 秒。

## 怎么验证生效

```bash
# 1. 看响应头：应出现 ETag、Last-Modified、Cache-Control
curl -sI 'http://<NAS-IP>:<端口>/api/media?file=/path/to/a.jpg'

# 2. 带上一步拿到的 ETag 再请求，期望 304 与 0 字节
curl -s -o /dev/null -w '%{http_code} %{size_download}\n' \
  -H 'If-None-Match: "<上一步的 ETag>"' \
  'http://<NAS-IP>:<端口>/api/media?file=/path/to/a.jpg'
```

换掉这张图（内容或修改时间变化）后再用旧 ETag 请求，应回 `200` 并重传完整内容。

浏览器侧：开发者工具 Network 面板里，图片的状态应为 `304` 或 `(disk cache)`，`Size` 列为 0 或极小。

## 已知限制

- 只有第二次及以后访问才省流量；首次访问仍要下载原图。列表直接加载原图、没有缩略图，首屏重量由原图体积决定。
- 不支持 `Range` 分部请求（大图拖动、视频类场景不适用这套缓存）。
- 压缩包内图片与 GIF 的有效期固定 3600 秒，过期后即使内容没变也会整份重传（这两个接口不处理条件请求）。
- 缓存标记为 `public`：浏览对游客开放，与静态资源共享同一口径。若将来改成「登录后才能看图」，应同步改成 `private`，否则共享代理会把图片缓存给未登录者。
- 修改时间精度依赖文件系统：部分文件系统只到秒级，故指纹里带上了文件大小作为补充。
- 反向代理若改写或剥离 `ETag` / `Cache-Control`，浏览器就拿不到指纹，会退回每次整份下载。

## 出问题时怎么判断

1. 「刷新还在重新下载」→ 先看 `/api/media` 的响应头有没有 `ETag`；有头但浏览器仍整份下载时，检查中间是否改写了缓存头。
2. 「换了图还看到旧图」→ 确认文件大小或修改时间确实变了（有的拷贝工具会保留源文件时间戳）；确认后强制刷新可立即生效。
3. 「304 之后图片空白」→ 检查是否有中间层把 304 转成了空的 200。
4. 「想调缓存时长」→ 改 `mediaCacheMaxAge` 后重启；只影响 `/api/media`。

# 安卓端自动更新设计稿

> 状态：**设计稿，未实施**。不新建任务、不下发，等确认后再排期。

## 一、目标

让已安装的 APK 能发现自己有新版本、下载并引导用户完成升级，不需要用户手动去 GitHub 找包。

成功标准：用户在设置页点「检查更新」→ 有新版本时显示版本号与更新说明 → 点更新下载 APK → 系统安装界面弹出 → 安装后版本号变化。

## 二、必须先厘清的一件事：网页版自动更新 ≠ APK 自动更新

同名但完全是两件事，混在一起设计会做错方向。

| | 网页版自动更新（现有） | APK 自动更新（本设计） |
|---|---|---|
| 更新对象 | **服务端 JS 代码** | **APK 二进制** |
| 机制 | `git pull` / GitHub 拉取 → 重启 node 进程 | 下载 APK → 调起系统安装器 |
| 触发方 | 服务端自己（定时任务） | 客户端（用户点或启动时检查） |
| 端点 | `GET /api/auto-update/status`、`POST /config`、`/check`、`/restart` | **本设计新增**，与上述互不复用 |
| 失败后果 | 服务端跑不起来 | 升级失败，旧版继续可用 |

**结论**：APK 更新不复用 `/api/auto-update/*` 那套端点，也不要往里面加分支。两者唯一的关系是「都叫自动更新」。

## 三、参考实现的关键设计（一个成熟的 Flutter Android 自更新项目）

它的做法值得抄的部分：

| 设计点 | 做法 | 我们是否采用 |
|---|---|---|
| 版本来源 | GitHub Releases API `/releases/latest` | 参考，但见下节选型 |
| 备用源 | API 不通时切镜像域名（`go.*` 查版本、`dl.*` 下载） | **采用思路**：我们要用自建服务端做主源 |
| 资产命名规范 | `{app}-{version}-{flavor}.apk`，用正则反解版本与 ABI | 采用（我们不区分 ABI，命名简化） |
| 完整性校验 | 资产带 **SHA-256**，下载后校验 | **必须采用** |
| 签名校验 | 安装前比对 APK 签名与已安装版本是否同一证书（返回 `signatureMismatch`） | **必须采用**（我们局域网是 HTTP，这层是唯一防线） |
| 按 ABI 分发 | arm64 / x64 两个 flavor | 首版不采用（我们单包，体积可接受） |
| 增量补丁 | 有 `fromVersion + sha256` 的差量包 | 首版不采用 |
| 传输安全 | 只接受 `https`（或 `http` + loopback） | **我们做不到**：局域网直连是 http，用签名校验兜底 |
| 安装方式 | 普通 `Intent.ACTION_VIEW` + 特权安装两条路径 | 只做普通路径（特权需系统签名或 root） |

## 四、方案选型：版本从哪查

### 候选

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A 自建服务端分发**（Lumigather 加两个端点） | 手机本来就连着服务端，不走外网；局域网内快；可控 | 服务端要存 APK；要自己写版本元数据 |
| **B GitHub Releases API** | 零服务端改动；与发布流程天然一致（我们已经在发 Release） | 手机能否访问 `api.github.com` 不确定（本机实测 200，但手机网络环境不同）；国内网络可能超时 |
| **C A 为主 + B 为辅** | 局域网稳定，外网可用时也能更新 | 两套逻辑要维护 |

**推荐 A**，理由：
- 用户手机一定连着 Lumigather 服务端（否则 App 没内容可看），但不一定能访问 GitHub
- 服务端加端点成本很低（读一个 JSON + 吐一个文件）
- 版本元数据由服务端自己维护，与「服务端已部署哪个版本」天然对齐

B 作为后续增强（若用户反馈希望在无局域网时也能更新）。

### A 方案的端点设计

```
GET /api/app/version
  免鉴权
  → 200 {
      "versionCode": 1120,
      "versionName": "0.0.2-1120",
      "sizeBytes": 7859033,
      "sha256": "34ae2296…",
      "releaseNotes": "新增压缩包浏览与 GIF 合成",
      "publishedAt": "2026-11-25T09:09:00+08:00",
      "downloadPath": "/api/app/download"
    }
  → 404 { "error": "服务端未提供 APK" }   没有可分发包时

GET /api/app/download
  免鉴权，返回 application/vnd.android.package-archive
  支持 Range 请求（断点续传）
```

APK 存放位置：服务端配置项指定目录（**不写死路径**），默认 `server/public/app/`；文件名带版本号避免缓存混淆，如 `lumigather-0.0.2-1120.apk`。

> 为什么免鉴权：App 可能在未登录状态下检查更新，且 APK 本身是公开可下载的产物（GitHub Release 也是公开的）。

## 五、客户端设计

### 1. 检查时机
- **设置页手动检查**（主要入口，MVP 必须有）
- 启动时静默检查（可选，首版可不做，避免每次冷启动都打一次请求）

不做「后台定时检查」—— 更新是低频事件，不值得常驻轮询。

### 2. 版本比较
用 `versionCode`（整数）比较，**不用 versionName 字符串**（`0.0.1-1119` 这种格式字符串比较会错）。
当前 `versionCode = 1119`，规则：`远端 versionCode > 本地 versionCode` 即有新版本。
同时校验 `远端 versionCode > 本地` 才允许升级，避免降级安装被系统拒绝。

### 3. 下载
- 下载到 `context.getExternalFilesDir(DIRECTORY_DOWNLOADS)` 或 `cacheDir`（**不用外部存储**，免权限）
- 显示进度（百分比 / 已下载字节）
- 支持取消；下载失败可重试（记录已下载字节做 Range 续传为增强项，首版可整包重下）
- 单文件 7-8 MB，局域网内秒级完成

### 4. 校验（两道，缺一不可）
1. **SHA-256**：与 `/api/app/version` 返回的 `sha256` 比对，不一致则删除文件并报错
2. **签名比对**：用 `PackageManager.getPackageArchiveInfo(path, GET_SIGNATURES)` 读取待装 APK 的签名，与当前已安装应用签名比对；不一致**拒绝安装**并提示「安装包签名与当前应用不一致，可能被篡改」

> 为什么签名校验必须做：我们走局域网 **HTTP**，没有 TLS。攻击者若能劫持局域网流量，就能替换 APK。SHA-256 也被劫持时可一起改，所以真正的防线是「签名必须是同一张证书」——那是攻击者拿不到的（私钥在私有仓）。

### 5. 安装
- Manifest 加 `<uses-permission android:name="android.permission.REQUEST_INSTALL_PACKAGES" />`
- 用 `FileProvider` 把文件路径转成 `content://` URI（`android:authorities="${applicationId}.fileprovider"`，配 `res/xml/file_paths.xml`）
- `Intent(ACTION_VIEW)` + `setDataAndType(uri, "application/vnd.android.package-archive")` + `FLAG_GRANT_READ_URI_PERMISSION`
- **Android 8.0+ 需用户授予「安装未知应用」权限**：先查 `packageManager.canRequestPackageInstalls()`，未授予时跳 `ACTION_MANAGE_UNKNOWN_APP_SOURCES` 设置页
- 系统安装界面需在设备上人工确认 —— **无法静默安装**（那需要系统签名或 root），这是平台限制，不要试图绕过

### 6. UI（复用现有组件）
- 设置页「关于」区：显示当前版本 + 「检查更新」按钮
- 检查中：按钮变「检查中…」禁用
- 有新版本：卡片显示 `新版本 0.0.2-1120`、更新说明、体积；按钮「下载并安装」
- 下载中：进度条 + 已下载/总大小 + 「取消」
- 校验失败 / 安装失败：内联红字给具体原因（复用现有错误展示模式，不弹 toast）
- 已是最新：「已是最新版本 0.0.1-1119」

## 六、风险与边界

| 风险 | 可能性 | 影响 | 缓解 |
|---|---|---|---|
| 局域网 HTTP 被劫持替换 APK | 低（局域网）+ 高（后果） | 装上恶意包 | **签名校验**（证书私钥在私有仓，攻击者拿不到） |
| 服务端没有 APK（未部署） | 高 | 检查更新 404 | 明确提示「服务端未提供安装包」，不算错误 |
| 用户拒绝「安装未知应用」权限 | 中 | 装不上 | 引导到系统设置页，给出可操作文案 |
| 下载中断 | 中 | 升级失败 | 重试；首版整包重下（7MB 成本可接受） |
| 存储空间不足 | 低 | 写入失败 | 写入前查可用空间，不足时提示 |
| 降级安装被系统拒 | 低 | 装不上 | 只允许 `远端 versionCode > 本地` |
| 多设备 ABI 差异 | 低 | — | 单包通用（不按 ABI 分发） |
| 服务端版本元数据与实际 APK 不一致 | 中 | 校验失败 | 元数据里的 sha256 由构建脚本生成，不手填 |

## 七、验收标准（实施时用）

1. 设置页能看到当前版本号，点「检查更新」有明确结果（有新版本 / 已最新 / 服务端无包 / 网络失败）
2. 有新版本时能下载到本地，`SHA-256` 与元数据一致
3. 签名不一致的 APK 会被拒绝并给出原因（可用故意改签名的包验证）
4. 下载完成后能调起系统安装界面，安装成功且版本号变化
5. 未授予「安装未知应用」时能正确引导到系统设置
6. 单测覆盖：版本比较（含边界）、SHA-256 不匹配、签名不匹配、网络失败、服务端 404
7. 检查更新不能污染全局提示槽（次要动作失败只用局部字段 —— `state-lifecycle-invariants` 判据 7）

## 八、不做什么（本次边界）

- **不做静默安装**（需系统签名/root）
- **不做增量补丁**（首版整包）
- **不做按 ABI 分发**（单包）
- **不做后台定时检查**（只做手动 + 可选启动时检查）
- **不复用 `/api/auto-update/*`**（那是服务端代码更新，语义不同）
- 不做 iOS / 桌面端更新

## 九、实施顺序建议（确认后）

1. **服务端**：`/api/app/version` + `/api/app/download` 两个端点 + APK 存放目录配置项
2. **构建脚本**：打包后自动生成版本元数据（含 sha256），落到服务端目录
3. **客户端**：版本检查 → 下载 → 校验 → 安装（分四步，每步可独立验证）
4. **UI**：设置页「关于」区
5. **回归**：不影响现有功能；检查更新的失败不污染全局提示

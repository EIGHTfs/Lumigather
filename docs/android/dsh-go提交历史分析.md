## 三、开发模式

### 3.1 明确以 AI 协作方式开发

证据：

| 证据 | 内容 |
|---|---|
| 提交 trailer | `Co-authored-by:` 52 次 |
| 工具署名 | 提交信息中出现 `Codex` 8 次、`cursor` 4 次 |
| 仓库内规范 | `AGENTS.md`（131 行）+ `.agents/` 目录 |

日均 118 提交这个量级，人工逐行写不可能达到，这是 AI 参与开发的典型形态。

### 3.2 提交信息写法

格式为标准 Conventional Commits，且**描述写到能看懂问题本身**：

```
fix(share-worker): publish-release 能在 Windows 发版机上跑 (#1297)
fix(android): Flutter 的 Surface 重新创建后再投一次刷新率
fix(tavern): 正在写的回复最多 50ms 重排一次；排队中已离开的显示请求不等帧就跳过
fix(plugins): 测试版只把 X.Y.Z 报给原生插件桥，不再被当成 0.0.0
release: 1.2.0 更新日志按 PR 内容改正
```

关键特征：不带「修复 bug」「优化代码」这类空话，直接写**具体现象 + 具体做法**（「最多 50ms 重排一次」「不等帧就跳过」「不再被当成 0.0.0」）。看提交信息就能知道改了什么、为什么改。

### 3.3 测试密度是高频迭代的前提

1758 个测试文件对 3409 个 Dart 文件（超过一半）。高频改动之所以能持续跑通，靠的是这个测试密度托底 —— 否则每天上百次改动必然把项目改崩。

## 四、可借鉴的做法

| 它的做法 | 我们的对应做法 |
|---|---|
| 测试文件占全量一半 | 安卓端业务代码一上手就配测试，不要等「写完了再补」 |
| 每天几十上百次小提交 | 按「骨架 → API → 列表 → 网格 → 大图」分步提交，每步可回滚 |
| fix 两倍于 feat | 承认「写出来就要改」是常态，不要指望一次写对 |
| 提交信息写具体现象 | 沿用我们已有的写法（如 `fix(start.sh): status 未解析 --port`） |
| 仓库内有 AGENTS.md | 我们跨会话/跨成员协作频繁，值得有一份项目级约定文件统一口径 |
| 鸿蒙优先于 iOS | 若要多端，鸿蒙的国内实用价值可能更高 |

## 五、不适用借鉴的部分

| 项 | 原因 |
|---|---|
| 提交频率 | 118 提交/天依赖 AI 全程参与 + 成熟架构，我们起步阶段强求这个频率只会制造混乱 |
| 版本节奏 | 1.3 天一个版本适合有大量用户的成熟产品快速响应用户；我们的安卓端还没有用户，发版频率应按里程碑走 |
| 代码组织 | 它是 Flutter 全家桶（9548 文件），我们的 MVP 只需千余行，过早上复杂分层会拖慢进度 |

# 安卓端架构边界与功能对齐

> 确立一条不可协商的架构边界，并用它约束后续所有功能开发。

## 一、核心原则：客户端零数据处理

**客户端（网页版、安卓 App）自身不做任何数据处理，数据处理全部交给后端。**

客户端的职责只有三件事：

1. 发 HTTP 请求
2. 渲染后端返回的结果
3. 维护交互状态（侧栏开合、选中项、加载中/失败）

「数据处理」的判定标准很宽 —— 只要一件事情的答案需要**看内容才能算出来**，它就属于后端：

| 类别 | 举例 | 归属 |
|---|---|---|
| 文件格式解析 | 解压 zip/rar/7z、读包内文件列表 | 后端 |
| 图像编解码与合成 | 序列帧合成 GIF、翻转 180°、缩略图生成、格式转换 | 后端 |
| 规则解析 | 解析 mod 的 ini、按 `$speed` 换算帧间隔、按包名 `@40ms` 推间隔 | 后端 |
| 目录遍历与过滤 | 递归扫描、黑名单排除、按扩展名筛选、按目录映射到分类 | 后端 |
| 排序与分页 | 排序规则、offset/limit 游标、总数统计 | 后端 |
| 权限判定 | 是否需要登录、能否写入某个目录 | 后端 |
| 文本检索 | 按文件名搜索、匹配规则 | 后端 |

### 为什么这条原则必须守住

- **唯一真相**：同一功能在网页和 App 各实现一遍，两份实现必然漂移。规则一改（比如 ini 的帧间隔算法调整），网页端生效而 App 还在用旧逻辑，用户看到两个不同的结果
- **端侧能力受限**：安卓端要在 App 里跑 7zz 就得打包二进制、要写 GIF 编码器、要移植 ini 解析 —— 每一项都是数周工作量，且无法保证与后端一致
- **可演进**：后端改进自动对所有客户端生效，不需要发版

### 反例（明确禁止）

- 在 App 里用 Kotlin 解压 zip 来列包内图片
- 在 App 里把多张 Bitmap 编码成 GIF
- 在 App 里解析 mod 的 ini 判断是否该翻转
- 在 App 里对后端返回的列表做二次筛选/排序（除非是纯视图层的即时过滤，且规则与后端一致）
- 在 App 里拼路径去猜某个文件存不存在

### 判据（写代码前自问）

> 这段逻辑如果后端改了规则，App 不同步更新会不会给出**不同的结果**？
> 会 → 说明它属于后端，客户端不该有。

## 二、功能对齐清单

网页版后端共 7 个模块。下表是安卓端现状与差距，作为后续排期的依据。

| 功能 | 后端端点 | 安卓端 | 差距 |
|---|---|---|---|
| 目录 / 图片列表 | `GET /api/directories`、`GET /api/images`、`GET /api/dir` | 已有（分类 → 网格 → 分页） | 无 |
| 原图输出 | `GET /api/media` | 已有 | 无 |
| 详情展示 | 复用图片列表字段 | 已有 | 无 |
| 下载存相册 | 复用 `GET /api/media` | 已有（MediaStore） | 无 |
| 登录 / 登出 | `POST /api/login`、`POST /api/logout` | 已有（token 持久化） | 无 |
| 收藏 | `GET /api/favorites`、`POST`、`DELETE` | 已有（增删查 + 右栏按钮三态） | 无 |
| 游客分组 | `GET /api/uploaded` | 已有（左栏虚拟视图） | 无 |
| 上传图片 | `POST /api/upload` | 无 | 缺 |
| 改密码 | `POST /api/change-password` | 无 | 缺 |
| 压缩包扫描 | `GET /api/zip/scan` | 无 | 缺 |
| 包内图片 | `GET /api/zip/img` | 无 | 缺 |

| 图片搜索 | **后端无端点**（见下节） | 仅能搜分类名 | 需先补后端 |

## 三、压缩包与 GIF 的实现归属（重点澄清）

这两块是项目差异化功能，容易被误判成「安卓端要重写」：

| 能力 | 实现位置 | 客户端要做的 |
|---|---|---|
| 列压缩包、列出包内图片 | 后端 `server/lib/archive.js`（spawn 7zz 解压，按 路径@mtime 缓存） | 调 `GET /api/zip/scan`，渲染列表 |
| 输出包内单张图 | 后端读完压缩包直接吐图片二进制 | 调 `GET /api/zip/img`，当普通图片加载 |
| 序列帧合成 GIF | 后端 `server/lib/gif.js`（含 mod ini 的 `$speed` 换算、包名 `@40ms` 推间隔、3DMigoto 翻转 180°） | 调 `GET /api/gif` 或 `/api/zip/gif`，把返回的 GIF 当图片显示 |

客户端不需要打包 7zz、不需要 GIF 编码器、不需要移植任何解析规则。

## 五、已知偏离本原则的现状

诚实记录一处：**网页版的图片搜索是前端本地过滤，不是后端检索。**

- 实现：`server/public/app.js` 的 `getFiltered()` 从 `[...apiImages, ...userImages]`（**已加载的图片**）里按 title / cat / name 做 `includes` 匹配
- 后端：**没有搜索端点**（`server/routes/` 与 `server/route/` 下均无 search/find 类路由）
- 由此产生的真实限制：**只能搜到「已经加载进列表的那部分」** —— 在 72,651 张的分类里搜文件名，未翻页加载的图搜不到
- 按本原则的正确形态应是：客户端把关键字传给后端，后端做全量检索并返回结果

因此安卓端做搜索时**不要照抄网页版的前端过滤**，而应先给后端补检索端点。若暂时只能做本地过滤，必须明确它只是「已加载数据的即时过滤」，并在界面上让用户知道范围受限。

## 六、把这条原则落实到代码的检查点

1. **数据层只做「请求 + 解析」**：`data/` 里的方法应当只有 HTTP 调用与字段映射，出现任何"计算"就要审视是否该放到后端
2. **UI 层不出现业务规则**：页面与组件只消费模型字段，不判断"这个文件该不该显示"「这张图该不该翻转」
3. **新增功能先问端点**：动手前先确认后端有没有现成端点；没有就先加后端，而不是在客户端实现
4. **列表的筛选排序**：若要做纯视图层的即时过滤（如本地搜索框过滤已加载项），规则必须与后端一致，且明确它是"已加载数据的即时过滤"而非"全量检索"

## 七、后续优化清单

本次不做、但不影响当前目标的问题，逐条记录供后续迭代。

| 问题 | 影响 | 优先级 |
|---|---|---|
| **文件夹层级**：网页端按目录层级逐层进入，安卓端目前是「分类 → 平铺全部图片」 | 大分类（7 万张）下无法按子目录缩小范围；与网页端的浏览习惯不一致 | 低（不影响主流程，但量大时体验差距明显） |
| 收藏列表无分页 | 服务端一次返回全量数组，收藏量上千时会一次性渲染 | 低（当前收藏量小） |
| 收藏页不能直接取消收藏 | 要先点开详情再点收藏按钮 | 低 |
| 游客上传项缺 `size` / 修改时间字段 | 详情页那两行显示 `—`（数据本就没有，不是漏读） | 低 |
| 图片搜索依赖后端检索端点 | 安卓端不做前端过滤（违反架构边界），需先给服务端加 `GET /api/search` | 中（等后端） |
| 子状态机尚未各自补独立单测 | 当前 96 条测试仍走 facade 验证 | 中（收益最大的一件事） |
| **`AppRoot.MainScaffold` 106 行**（混了手势进度/渐变/主界面变换/遮罩/两侧栏五件事） | 改任一层都要在百行里找段落；已在 `.auditignore` 临时标注，属技术债 | 中（需专门一轮 + 真机回归） |
| `HomeUiState.kt` 仍同文件放状态契约 + facade | 纯搬运、无行为收益，故未拆 | 低 |
| token 明文存 SharedPreferences | 需引 androidx.security 才能加密 | 低 |

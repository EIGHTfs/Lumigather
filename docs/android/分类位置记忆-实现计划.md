# 分类位置记忆 · 实现计划

> 本文只是计划，**本轮不改任何 Kotlin 代码、不加测试**。
> 调研对象：`server/public/app.js`（网页版参考实现），客户端现状取 T20 交付后的 `android` 分支。

## 门禁表

| 项 | 内容 |
|---|---|
| 任务 | 让 APP 记住「每个分类上次停在哪个目录」，切回该分类时直接回到那一层 |
| 验收标准 | ①按分类各记一条路径；②切回该分类恢复；③路径失效时回退而不是显示空目录；④数据按服务器地址隔离 |
| 不做什么 | 不做路径前进/后退按钮（网页版有，但那是内存态历史栈，本任务不含）；不做"自动进入唯一子目录"；不改服务端 |

## 一、目标

改成文件夹层级浏览后暴露一个体验缺口：**切走再切回分类，永远回到根目录**，用户要重新一层层点进去。网页版刷新和切分类都能停在原处。

期望效果：切回某分类 → 直接呈现在上次停留的那一层（面包屑与该层内容一致）；换服务器 → 两套路径互不污染；路径被删 → 退回最近存在的父级，而不是空白页。

## 二、网页版机制对照（逐条带证据）

### 2.1 `localStorage` 里存了哪几个 key、结构是什么

| key | 结构 | 与本功能相关 |
|---|---|---|
| `galleryNav` | `{ activeDir: string \| null, navByDir: { [rootPath]: relativePath } }` | **是**（唯一相关的） |
| `ZIPS_KEY` / `GROUPS_KEY` / `TREENODES_KEY` | 字符串数组（折叠的包 / 展开的分组 / 折叠的树节点） | 否（压缩包与目录树折叠态） |
| `galleryLang` | 语言串，如 `"zh-CN"` | 否 |

证据：
- 写入 `galleryNav`：`app.js:975-984`
  ```js
  function saveNav() {
    if (activeDir) navByDir[activeDir] = currentPath;
    localStorage.setItem("galleryNav", JSON.stringify({ activeDir, navByDir }));
  }
  ```
- 读取：`app.js:1020-1031`（`restoreNav`）
- 另外三个 key 见 `app.js:189-201`，语言见 `app.js:207-213`

**注意两点**：
1. `navHistory`（路径历史栈，`app.js:161-163`）**不持久化**，只在内存里，刷新即丢。所以"前进/后退"不是记忆功能的一部分。
2. `activeFilter` 也没进 `galleryNav`，只剩内存；`switchDir` 里还会把它强制重置为 `"all"`（`app.js:1039`）。**筛选状态不被记忆**。

### 2.2 是「每个分类各记一个位置」还是「全局只记最后一个」

**每个分类各记一个**。`navByDir` 是 `rootPath → relativePath` 的映射（`app.js:1018` 的声明，注释写明"每个根目录各自记录的 currentPath"），`saveNav` 每次把"当前分类 + 当前路径"写进这个映射（`app.js:977`）。

`activeDir` 额外记"最后看的是哪个分类"，用来决定刷新后回到哪个分类（`app.js:1026-1029`）。

### 2.3 何时写入

**每次导航都写**，写一次就是一次 `localStorage.setItem`（同步 IO）：

| 触发 | 证据 |
|---|---|
| 进子目录 | `app.js:1545`、`1553`、`1589`、`1627`、`1669-1671`、`1688-1690` |
| 面包屑回根/上级 | `app.js:826-830`、`836-840`、`846-850` |
| 切分类 | `app.js:1040`（`switchDir` 内） |
| 前进/后退 | `app.js:1004`、`1013` |
| 自动进入唯一子目录 | `app.js:1431-1432` |

即：**没有节流、没有离开时批量写**，纯"点一下写一次"。

### 2.4 恢复时机

| 时机 | 行为 | 证据 |
|---|---|---|
| 页面启动/刷新 | `restoreNav()` 读 `galleryNav`，**在首次 `render()` 之前**执行 | `app.js:473-476`（注释说明放在 render 之后"首屏会先闪一下主页再跳回"） |
| 切换分类 | `switchDir(newDir)` 读**内存**里的 `navByDir`，不读盘 | `app.js:1034-1045` |
| URL `?dir=` | 优先级**高于** localStorage：从 `directories` 里按 root 名后缀匹配，剩余部分作 `currentPath` | `app.js:477-493`；用完即从地址栏清掉（`:496`） |

也就是说：**localStorage 只在冷启动读一次**，热切换靠内存映射。

### 2.5 位置失效怎么处理

| 失效类型 | 网页版行为 | 证据 |
|---|---|---|
| 记住的**分类**不存在了 | 忽略这条记录（`directories.some(d => d.path === o.activeDir)` 不匹配就跳过） | `app.js:1026` |
| 记住的**分类还在、路径被删/改名** | **不校验、直接用**：`currentPath = navByDir[activeDir] \|\| ""`，只在"没这条记录"时回根 | `app.js:1028`、`1038` |
| 该路径 `/api/dir` 查不到 | 服务端对不存在路径返回**空目录**（`server/routes/browse.js:289-291`） | 界面表现为"这个分类是空的" |

**结论：网页版在这里是缺陷** —— 它只在"路径字符串为空"时回根，不做"路径是否真实存在"的校验，目录被删后会停在一个看起来空的页面上，用户只能手动点面包屑回退。

Android 侧要在这一点上做对（见 §3.5），否则只是把网页版的毛病搬过来。

### 2.6 调研小结（三个容易被忽略的事实）

1. **记忆的是"相对分类根的路径"，不是绝对路径** —— 好处是分类根换了位置（盘符/挂载点变化）记忆仍然有效。
2. **只记分类维度，不记全局"最后位置"** —— 必须按分类分栏存。
3. **历史栈不持久化** —— 别把"能前进后退"和"记住位置"混成一个功能。

## 三、Android 侧方案

### 3.1 存什么

| 字段 | 取值 | 理由 |
|---|---|---|
| 服务器标识 | 当前 baseUrl（规范化后，如 `http://10.10.10.64:8081`） | 不同服务器的路径体系完全不同，混存会互相污染 |
| 分类标识 | **分类根绝对路径**（`CategoryView.rootPath`） | 与网页版一致；比分类名稳定（分类可改名，目录通常不动） |
| 路径 | 相对分类根的路径串（`"Mods/.Mods"`，根 = `""`） | 与 `BrowseController.pathStack.joinToString("/")` 完全一致，无需转换 |

**不存**筛选状态（收藏/游客）、不存放大态（`expandedEntryKey`）、不存历史栈 —— 与网页版对齐，且这些都已有各自的清理时机。

### 3.2 存在哪：新增 `DirMemoryStore`（沿用现有存储抽象）

项目已有的存储模式是「common 里接口 + `expect` 工厂，androidMain 用 SharedPreferences 实现」，两个现成例子：

- `ui/screens/settings/ServerAddressStore.kt`（`interface` + `expect fun createServerAddressStore()`）
- `data/AuthTokenStore.kt`（`interface` + `expect fun createAuthTokenStore()`）

**新增**：

| 文件 | 内容 |
|---|---|
| `android/shared/src/commonMain/kotlin/data/DirMemoryStore.kt` | `interface DirMemoryStore` + `expect fun createDirMemoryStore(): DirMemoryStore` |
| `android/shared/src/androidMain/kotlin/data/DirMemoryStore.android.kt` | SharedPreferences 实现 |

接口（草案）：

```kotlin
interface DirMemoryStore {
    /** 读某服务器下某分类上次停留的相对路径；没有记录返回 ""（= 根） */
    fun readLastPath(serverKey: String, categoryRoot: String): String

    /** 记一次位置；实现内部做合并，避免每次导航重写整个表 */
    fun writeLastPath(serverKey: String, categoryRoot: String, relativePath: String)

    /** 清掉某服务器的全部记录（换服务器/清地址时用） */
    fun clearServer(serverKey: String)
}
```

存储落地：**复用已有的 `lumigather_settings_v1` SharedPreferences 文件**（与地址、登录态同文件），新增一个键：

```
KEY_DIR_MEMORY = "dir_memory_v1"
值 = JSON: { "<serverKey>": { "<categoryRoot>": "<relativePath>" } }
```

为什么复用同一个文件：`ServerAddressStore.android.kt` 顶部注释已写明"两处各写一份字面量迟早会漂移"，同一份配置数据放同一文件、键名各自收成常量。

**为什么不用 `androidx.datastore`/Room**：本需求是几十条字符串，引入新依赖与异步 API 换不来收益；同步读一次对首屏无影响（且恢复发生在分类加载之后，不在启动关键路径上）。

### 3.3 key 怎么设计（多服务器隔离）

```
serverKey  = 规范化后的 baseUrl（去掉末尾 /，小写 host）
categoryKey = CategoryView.rootPath
```

- **为什么必须隔离**：换服务器后 rootPath 可能恰好同名（两台机器都配 `/volume6/Game.Patch N MOD`），但内容完全不同 —— 不隔离会"记住一个不存在的层级"。
- **为什么用 rootPath 做二级 key 而不是分类名**：分类名是展示层概念，改名后记忆全废；rootPath 变了的概率更低，且变了就是真的换目录，记忆本应失效。
- **清理**：`clearServer(serverKey)` 在"用户清空/修改服务器地址"时调用（挂在 `SettingsController.saveAddress` 的成功分支）；迁移/重装无需处理（同文件同键）。

### 3.4 何时写 / 何时读

**读：只在"切到某个分类"时读一次**（不是启动时）。

- 挂载点：`BrowseController.loadCategory(categoryName)` 开头，清栈之后、加载之前，读 `readLastPath(serverKey, rootPath)` 并预填 `pathStack`。
- 不在启动时读：启动时分类还没加载出来（不知道要看哪个分类），网页版之所以能启动恢复是因为它额外记了 `activeDir`；我们**没必要**记"最后看哪个分类"——App 启动默认看第一个分类，这个行为改动面更大且不在本任务内（见 §7 待决策）。

**写：每次"层变化成功"后写一次**。

- 挂载点：`BrowseController.loadCurrentDir(...)` 拿到 `ApiResult.Ok` 之后，写 `writeLastPath(serverKey, rootPath, currentRelativePath())`。
- 为什么不是每次点都写：`loadCurrentDir` 只在"实际换了层"时被调用（进/退/跳回/切分类），频率 = 用户导航次数，与网页版一致；**不需要额外节流**。
- 为什么不写在 `loadCategory` 之后：恢复失败的场景（§3.5）需要把"回退后的真实路径"写回去，所以写在"拿到结果之后"才覆盖到正确值。

**写入失败必须静默**：存储只是增强，`writeText` 抛异常（磁盘满/权限）时不能让导航崩 —— 用 `runCatching` 吞掉并保留内存行为。

### 3.5 失效处理（比网页版多做一步）

存的路径可能指向已被删除/改名的目录。策略：**逐级回退到最近存在的父级，一直退到分类根**。

实现位置：`BrowseController` 内部，与恢复同一处。

```
候选路径 = [存的原路径, 上一级, 再上一级, ..., ""]
for 候选 in 候选路径:
    加载该层（调用 /api/dir）
    如果 该层有内容（dirEntries 非空 或 images 非空 或 有压缩包）:
        pathStack = 该候选拆分出的段
        写回 writeLastPath(候选)
        return
如果全空:
    pathStack = 空（根），写回 ""
```

约束：
- **最多回退 N 级**（建议 3），避免深层路径逐级请求拖慢切分类；超过 N 级直接回根。
- 每一级都是一次 `/api/dir`，所以回退上限必须有；正常情况第一级就命中。
- "该层有内容"的判据要包含压缩包（有的目录只有包没有图，见 `isContentEmpty` 的既有语义）。
- 若"整层确实为空但路径真实存在"（用户上次停在空目录），回退会一路退到根 —— 这是可接受的降级（空目录本身没什么可看）。

### 3.6 清理

| 场景 | 处理 |
|---|---|
| 换服务器地址 | 读到新 baseUrl 自然换 key（**不清旧记录**，用户可能切回来）；可选提供"清空此服务器记忆"由设置页触发（本任务不做） |
| 分类被删除 | 记录成为孤儿键，体积可忽略；下次 `clearServer` 或重装自然消失（不做主动 GC） |
| 服务器不可用 | 恢复发生在分类加载成功之后，服务器挂了根本走不到恢复逻辑 |

### 4.1 改动面

| 文件 | 改什么 | 为什么必须改这里 |
|---|---|---|
| `android/shared/src/commonMain/kotlin/data/DirMemoryStore.kt`（新增） | 接口 + `expect` 工厂 | 存储抽象（沿用 `ServerAddressStore` 模式） |
| `android/shared/src/androidMain/kotlin/data/DirMemoryStore.android.kt`（新增） | SharedPreferences 实现 + JSON 编解码 | 平台差异只能落 here |
| `android/shared/src/commonMain/kotlin/ui/screens/state/BrowseController.kt` | 构造参数 + `restoreDirMemory()` / `persistDirMemory()` / 回退循环 | **目录栈 `pathStack` 是这里私有的**，恢复/保存只有在这一层才算"不泄露给 UI" |
| `android/shared/src/commonMain/kotlin/ui/screens/state/HomeUiState.kt` | 构造参数加 `dirMemoryStoreProvider`，构造 `browse` 时传入 | 依赖注入链（与现有 `addressStore` / `authTokenStore` 同一处） |
| `androidUnitTest/...`（新增 1~2 个类） | 单测 | — |

**总计 5 个文件（3 改 2 新 + 测试），全部落在状态层与数据层。**

### 4.2 为什么不需要动 UI（低耦合判定的关键）

- 恢复发生在 `loadCategory` 内部：UI 切分类只调 `selectFilter(Category)` → facade → `browse.loadCategory`，恢复对 UI 是透明的。
- 保存发生在 `loadCurrentDir` 内部：UI 进目录只调 `enterFolder`，保存对 UI 是透明的。
- **UI 层不需要感知"记忆"这件事**：没有"恢复/保存"的调用点要加在 `HomeScreen` / `AppRoot`，也不需要新回调。
- 面包屑、`canGoUp`、`dirEntries` 都由既有的 `publishBreadcrumbs` / `loadCurrentDir` 产出，恢复后自动一致。

**判定：方案通过。** 如果实施时发现要给 `HomeScreen` 传 `restore`/`persist` 回调，说明挂错层了 —— 应回到 `BrowseController` 内部解决。

### 4.3 与既有清理逻辑的关系（不要重复清）

`expandedEntryKey`（放大态）已有 6 处清空（T20）。本方案的恢复走的是同一个 `loadCurrentDir`，因此**放大态会被既有逻辑顺手清掉**，不需要为记忆功能新增清理。

## 五、风险与边界

| 风险 | 可能性 | 影响 | 缓解 |
|---|---|---|---|
| 陈旧位置（目录被删/改名） | 高 | 停在"空目录" | §3.5 逐级回退（上限 3 级，保底回根） |
| 频繁写盘 | 低 | 卡顿 | 只在层变化后写一次（= 用户导航次数）；JSON 表只有几十条字符串；`apply()` 异步提交 |
| 多服务器/多分类数据膨胀 | 低 | 存储缓慢增长 | 每条记录 < 60 字节；提供 `clearServer`；孤儿键不主动 GC（可忽略） |
| 与 `expandedEntryKey` 打架 | 低 | 进目录莫名放大 | 已由 T20 的清空逻辑覆盖；单测回归一条即可 |
| 恢复导致首屏慢 | 低 | 切分类多一次 RTT | 恢复与扫包并行（复用现有 `loadLayerAndArchives` 的并行路径）；回退上限 3 级 |
| 存储读写异常 | 中 | 崩溃 | 读写都 `runCatching`，失败退化为"不记忆" |
| 服务器地址含端口差异（`http://h:8081` vs `http://h:8081/`） | 中 | 记忆命中失败 | `serverKey` 规范化：去尾斜杠、host 小写（复用 `ServerAddressRules` 的既有规范化） |

边界条件：
- **没有任何记录** → 走根目录（等价于当前行为）
- **记录为空串** → 根目录，不触发回退
- **记录路径超长/含非法字符** → 交给 `UrlBuilder` 编码；服务端返回错误 → 回退链兜底
- **并发**：恢复与保存都在 `BrowseController` 单协程内顺序执行，无并发写同一 key

## 六、分步实施建议（从简到难，每步可独立验收）

| 步 | 内容 | 验收 |
|---|---|---|
| 1 | `DirMemoryStore` 接口 + Android 实现 + 假存储单测 | 读写/覆盖/`clearServer` 三态；换 serverKey 互不影响 |
| 2 | `HomeStateHolder` 注入 + `BrowseController` 保存（每次 `loadCurrentDir` 成功后写） | 单测：进两层目录后，store 里记录为 `A/B` |
| 3 | `BrowseController.loadCategory` 恢复（读 → 预填 pathStack → 加载） | 单测：切走再切回同分类，`breadcrumbs` 与 `gridEntries` 回到该层 |
| 4 | 失效回退（逐级，上限 3） | 单测：store 里存 `Deleted/Deep`，服务端这两层都空 → 回退到 `Deleted`（若有内容）或根，且写回纠正后的路径 |
| 5 | 清理（换服务器时 `clearServer`；可选） | 单测：换地址后再切回，新服务器下不出现旧记忆 |

每步都能独立跑测试，不需要一次做完。

## 七、需要你决策的三个点

1. **要不要同时记住"最后看的哪个分类"**（网页版记了 `activeDir`，所以它能启动即恢复）。
   本计划**不做**：App 启动默认第一个分类是既有行为，改它属于另一件事。若要做，会多一个字段与一条启动恢复路径。
2. **是否连筛选状态一起记**（收藏/游客 vs 某分类）。本计划**不记**（与网页版一致：`activeFilter` 不持久化）。
3. **回退上限取几级**（建议 3）。取值越大越"聪明"，但切分类时最坏会多发 3 个 `/api/dir`。

## 八、后续优化清单（本任务不做）

- 路径前进/后退按钮（网页版有内存栈，Android 侧需另设计持久化，否则重启即丢）
- 网页版的"自动进入唯一子目录"（`app.js:1428-1434`）：我们目前用"叶子目录摊图"覆盖了大部分场景，真正的单链深层目录仍要手动点
- 设置页加「清空此服务器的位置记忆」入口
- 记忆条数上限与 LRU 清理（当前量级不需要）

## 附：与网页版的行为差异（有意为之）

| 差异 | 网页版 | 本计划 | 原因 |
|---|---|---|---|
| 路径失效 | 直接使用，可能停在空目录 | 逐级回退到最近存在的父级 | 网页版的已知缺陷（§2.5） |
| 多服务器隔离 | 没有（不同端口的同一套 localStorage 会混） | `serverKey` 分栏 | 用户可能连不同服务器 |
| 写入时机 | 每次导航写整个 JSON | 同样每次导航，但只写一次且 `apply()` 异步 | 减少主线程 IO 风险 |

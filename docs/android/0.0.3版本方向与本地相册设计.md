## 二、本地图片入口：参考什么、不参考什么

参考对象（一个 Flutter Android 客户端）把「本地」作为一种**宿主机类型**：

```dart
enum HostKind { local, ssh, relay }
HostKind.local => "这台手机"
```

它选「本地」时会**在本机启动一个服务进程**，App 连自己的 localhost —— 因为它要跑的是同一个后端。

**我们的本地模式不同，也更简单**：不启动任何服务，**直接读手机相册**。所以：

| 维度 | 参考对象 | 我们 |
|---|---|---|
| 「本地」是什么 | 一个宿主机（跑在手机上的服务） | **手机相册这个数据源本身** |
| 需要进程吗 | 需要 | **不需要** |
| 数据来源 | 本地服务的 API | `MediaStore` 直接查 |
| 要写的代码 | 进程管理 + 连接 + API | 权限 + 查询 + 适配器扩展 |

**唯一要借的是「它是一个与远程服务器并列的内容源」这个概念**，而不是它的实现。

## 三、入口形态：数据源切换，不是筛选列表里的一项

参考对象（同上那个 Flutter 客户端）的实际形态是这样的：

- **底部状态栏**显示当前主机（`💻 VirtualDSM` + `● LAN 局域网`），点开是切换面板
- **切换弹层**标题「切换主机」，每项 = 图标 + 名称 + 副标题 + **状态点**：
  - 「本机 / 这台手机上的 DSH / ● 已停止」
  - 「VirtualDSM / 远程 · Linux / ● 已连接 ✓」
- 弹层下方还有其它入口（管理远程主机等）
- 左栏那一列是**远程数据源内部的筛选**（全部对话 / 运行中 / 待确认 / 未读），与主机切换分属两层

**结论**：数据源（本地 vs 远程）是**独立层级**，不是筛选列表的第四项。硬塞进同一个列表会让「换数据源」和「换筛选」看起来是同一件事。

### 我们的形态

| 层 | 位置 | 内容 |
|---|---|---|
| **数据源** | 底部状态栏 + 点开的切换弹层 | 远程服务器 / 本地相册 |
| **筛选** | 左栏 | 收藏 / 游客 / 8 个游戏分类（**仅在远程数据源下有意义**） |

底部状态栏现在显示的是「站点名 · 在线 · 版本」，改成数据源指示器（如「● 远程 · VirtualDSM」/「● 本地相册」），点开弹层切换 —— 与参考对象一致。

## 三之二、模型：用密封类把「筛选」关进「远程」里

当前模型（0.0.2 已落地）：

```kotlin
sealed interface ContentFilter {
    data class Category(val name: String) : ContentFilter
    data object Favorites : ContentFilter
    data object Guest : ContentFilter
}
```

在它外面包一层数据源：

```kotlin
sealed interface ContentSource {
    data class Remote(val filter: ContentFilter) : ContentSource   // 远程：带筛选
    data object LocalAlbum : ContentSource                          // 本地：无筛选
}
```

**为什么不是"加一个 source 字段 + 保留 filter 字段"**：那正是 0.0.2 修掉的 bug 形态（两个字段各写一半就会不一致）。
把 `filter` **包进** `Remote` 里之后，「本地相册下还残留一个分类筛选」这种半状态**从类型上就不存在** —— 想读 filter 必须先证明自己在 Remote 分支里。

对应改动：
- 左栏保持原样（它只服务远程筛选）；数据源不是本地时，左栏的筛选区不显示
- `selectSource(target: ContentSource)` 作为唯一入口；`Remote(Category(x))` / `Remote(Favorites)` 等复用现有 `selectFilter` 的逻辑
- 远程相关的派生出口（分类标题、扫包、收藏计数）在 `LocalAlbum` 下返回空/不触发
- 切到本地相册时，不请求任何远程接口；切回远程时按需重载

## 四、关键技术前提：图片适配器要支持 `content://`

**这是最可能翻车的地方，必须先解决**。

现有 `LumigatherImageAdapter` 只认四种 scheme：

```
isWebUrl()   http/https
isBase64()   data:image/...
isAssets()   assets://
isFile()     file://
```

而相册图片的地址是 `content://media/external/images/media/{id}` —— **当前会走到 `else -> null`，图片永远不显示**。

要做的：在 `loadDrawable` 的 when 分支里加一条 content 分支，用
`context.contentResolver.openInputStream(uri)` 读字节，再走现有的两段式采样解码（不要另写一套解码）。

> 这类「编译与启动都正常、图片永远空白」的失败形态本项目已经踩过两次（`KRImageAdapter` 未注册、`AsyncImagePainter` 条件渲染死锁），所以这条要作为**独立验收项**，不能混在功能里一起验。

## 五、权限

| 系统版本 | 权限 | 说明 |
|---|---|---|
| Android 13（API 33）及以上 | `READ_MEDIA_IMAGES` | 新的细分媒体权限 |
| Android 12 及以下 | `READ_EXTERNAL_STORAGE` | 现有声明是 `maxSdkVersion="28"`（当初只为旧版下载），要**扩到 32** |

当前 `targetSdk = 32`，所以 Android 13 设备上系统仍按旧模型要 `READ_EXTERNAL_STORAGE`；但用户手机可能是 13/14，**两个都声明**才稳。

行为要求：
- 拒绝权限 → 该筛选下显示「需要相册访问权限」+ 一个按钮跳系统设置（不要静默空白，也不要弹 toast）
- 权限被撤销（Android 11+ 有一次性授权）→ 回到该筛选时重新检查，不能缓存"已授权"

## 六、数据查询与分页

- 数据源：`MediaStore.Images.Media.EXTERNAL_CONTENT_URI`
- 排序：`DATE_ADDED DESC`（最近的照片在前）
- 字段：`_ID`（拼 content URI）、`DISPLAY_NAME`（文件名）、`SIZE`、`DATE_MODIFIED`、`WIDTH`/`HEIGHT`
- 分页：**必须分页**。手机相册几万张是常态，一次性查全部会 OOM/卡死
  - API 30+ 用 `Bundle` 传 `QUERY_ARG_LIMIT` / `QUERY_ARG_OFFSET`
  - API 24–29 用 `sortOrder` 拼 `LIMIT n OFFSET m`（可用，但要在注释里标明这是兼容写法）
- 每页大小沿用现有的网格分页常量，不要另设一个

**映射成现有 `ImageItem`**：`name` / `absoluteUrl`（content URI）/ `sizeText` / `modifiedIso` 都有，详情页可直接复用。

## 七、交互差异（本地图不是远程图，别硬套）

| 能力 | 远程图 | 本地相册图 |
|---|---|---|
| 浏览 / 详情 | ✅ | ✅ 复用 |
| 下载存相册 | ✅ | **隐藏** —— 图本来就在相册里 |
| 收藏 | ✅ | **首版隐藏**：收藏是服务端概念，本地图要先上传才能收藏（上传功能未做） |
| 分享 | 未做 | 首版也不做 |
| 压缩包扫描 | ✅ 只在分类视图 | **不触发** |

右栏那排动作按钮要按**数据源**决定显示哪些 —— 这是「同一组件在不同数据源下能力不同」，用参数控制（如 `actions = RemoteActions / LocalActions`），不要在组件内部判断具体来源类型。

## 八、边界与风险

| 风险 | 可能性 | 影响 | 缓解 |
|---|---|---|---|
| **适配器不支持 content://** | 确定（当前就不支持） | 本地相册全是空白格 | 先扩展适配器，作为独立验收项 |
| 相册几万张一次性加载 | 高（不处理必然） | 卡死 / OOM | 强制分页；滚动触底加载 |
| 权限拒绝 | 中 | 空白页 | 明确空态 + 跳设置 |
| 权限被撤销 | 中 | 点进去空白 | 每次进入重新检查 |
| 老系统 `LIMIT/OFFSET` 拼接兼容性 | 中 | 分页错乱 | API 30 分支与兼容分支都要测；不行就退回 cursor 游标分页 |
| 大图（几十 MB 原图）解码 OOM | 中 | 崩 | 沿用现有的两段式采样解码，目标尺寸给网格尺寸 |
| 本地图与远程图混在同一 LruCache | 低 | 缓存污染、命中率下降 | 缓存 key 已含 URL，content URI 天然隔离 |

## 九、验收标准（实施时用）

1. 左栏出现「本地相册」，点进去能看到手机照片（**不是空白格**）
2. **底部状态栏能切换「远程 / 本地相册」**，切换后左栏的筛选区在本地模式下不显示、远程模式下恢复且保留原来的分类
3. 滚动触底能加载更多，几万张时不卡死
3. 点图能看详情（文件名、大小、修改时间正确）
4. 拒绝权限 → 显示可操作提示；授权后能正常显示
5. 右栏不出现「下载」（本地图不需要存相册）
6. 切回远程分类/收藏/游客一切正常（说明筛选值没有半状态）
7. 单测覆盖：权限状态映射、MediaStore 行 → ImageItem 映射（含字段缺失的兜底）、分页游标推进、筛选切换后远程状态不被污染

## 十、不做什么（本次边界）

- **不做**本地图上传到服务器（那是「上传」批次的事）
- **不做**本地图收藏（依赖上传）
- **不做**本地相册的按文件夹/相册分类浏览（只做一个扁平列表，按时间倒序）
- **不做**本地视频（只做图片）
- **不做**相册内搜索

## 十一、实施顺序建议（确认后）

1. **适配器加 content:// 支持**（独立提交，可单独验证：用任意 content URI 确认能显示）
2. **权限声明与运行时申请**（两个权限 + 拒绝态 UI）
3. **MediaStore 查询与分页**（先不分页跑通，再加分页）
4. **底部状态栏改成数据源指示器 + 切换弹层**（对齐参考实现的位置：状态栏显示当前数据源，点开弹层选）
5. **接入 `ContentSource.LocalAlbum`**（左栏筛选区在本地模式隐藏、派生出口切换）
6. **右栏动作按数据源裁剪**（隐藏下载/收藏）
7. **回归**：远程侧的筛选、收藏、压缩包在切回后表现不变

## 十二、附录：连接通道的演进空间

本文讨论的「远程 vs 本地」里，远程目前只有一种通道：**局域网 HTTP 直连**。参考实现在这块做得更厚，值得记下它的结构，作为未来若要做外网访问时的参考。

### 参考实现的三通道 + 一个统一出口

| 通道 | 机制 |
|---|---|
| 本地 | 在手机上起服务进程，连 localhost |
| SSH | `remote/ssh/`：SSH 隧道把远端端点变成本地可访问的 baseUri |
| relay | `remote/relay/`：WebRTC P2P 打洞，直连失败才走中继服务器 |

关键在**统一出口**：不管哪种通道，上层最终都是
`DshClient.connect(baseUri, token)` —— 聊天/终端/文件操作都不知道自己连的是本机、SSH 还是 relay。
**加一种通道 = 只改「怎么得到 baseUri」，业务代码零改动。**

### 我们现在的形态（已经具备这个解耦）

| 层 | 现状 |
|---|---|
| 业务 API | `ApiClient(baseUrl)` —— 只认 baseUrl，不知道底下怎么连的 |
| 传输 | `HttpTransport` 接口 + `OkHttpHttpTransport` 实现 |
| 通道 | 局域网 HTTP 直连（一种） |

`baseUrl` 就是我们的统一出口。将来加通道，只要能「得到可用的 baseUrl」，业务层同样不用动。

### 未来三条路（现在都不做）

| 方案 | 成本 | 说明 |
|---|---|---|
| 端口转发 / VPN / 内网穿透（Tailscale、ZeroTier 等） | 最低 | 用户侧解决，App 零改动 —— 仍然只是填一个 http 地址 |
| relay 中继 | 高 | 穿透任意 NAT，但要自建中继服务 + 鉴权体系 |
| WebRTC P2P | 最高 | 打洞 + 中继兜底，工程量与维护成本都不小 |

**判断**：这个项目的场景是「在局域网里看 NAS 上的图」，外网访问属可选增强。真要做，**优先推荐现成的 VPN/内网穿透**，App 侧零改动；自建 relay 或 P2P 不划算（要长期维护中继服务，而收益只是省掉用户配一条网络）。
